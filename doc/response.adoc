[#wasi-response]
== The response

`webcpp::wasi::http::response`, in `<webcpp/wasi/http/response.hpp>`, is
what a main returns: an aggregate of three members, each with a default, so
that a designated initializer names only what differs from it, as
`{.status = 404}` does.

[cols="1,1,3",options="header"]
|===
| Member | Type | What it holds

| `status`
| `unsigned`, 200 by default
| The status, sent as it is. Keep it within 100 to 599, the codes
  `wasi:http` accepts.

| `content_type`
| `std::string_view`, empty by default
| The `content-type` header, sent only when it is not empty. It is read
  after the main has returned, so it views a string literal, such as
  `"application/json"`, or the method or the target, never a string of the
  main's own.

| `body`
| `std::string`, empty by default
| The body, sent whole, however long.
|===

The handler sends no other header (<<wasi-invariant-7,guarantee 7>>). A
`content_type` is a view rather than a string because it is nearly always a
literal: a view of one costs nothing, where a `std::string` of
`"application/json"`, 16 characters, would allocate on wasm32, where
`libc++` keeps at most 10 in the string itself.

`response.hpp` includes nothing of the component ABI, and compiles natively
too: the rest of a program builds responses, holds them and passes them
around, as messages between actors for example, and is tested natively,
without a WASI toolchain.
